# GPT-6 Astra prompting principles (authoritative)

The consult target is **GPT-6 Astra**, driven through ChatGPT web at the top reasoning tier. As of 2026-09-06 the live composer offers a power slider — `Instant / Medium / High / Extra High / Pro` — plus a separate model list reading `Latest` (checked) / `GPT-5.6 Sol` / `GPT-5.5`, with the composer badge showing "6". **Our GPT-6 Pro path is therefore `Latest` + `Pro`.** That mapping is a well-evidenced inference from the badge and the list ordering, *not* an OpenAI-documented fact: OpenAI has published no help-center article naming a `Latest` picker entry, and no source states that the web "Pro" rung maps to the API's `reasoning.mode:"pro"` on `gpt-6-astra`. Treat it as our best read, and re-check it against the live UI if selection ever misses. `Pro Extended` no longer exists in this build.

Prompt Astra the way OpenAI says to prompt 5.x/6 reasoning models — outcome-first — NOT the GPT-4-era process-heavy way. Astra's own guide adds *behavioral* patches on top of that (initiative, instruction-sensitivity, style); it does not change the structural advice.

## Carried forward from 5.6 (not restated for Astra, not contradicted either)

OpenAI's Astra guide does not repeat the 5.6 "favor leaner prompts" / `text.verbosity` material. Absence of restatement is not a reversal, and nothing in the Astra guide argues the other way, so these stand as our law until a source retracts them. Flag them as carried-forward, not Astra-confirmed, if you cite them.

- **Outcome-first, not process-heavy.** Define the destination (goal, success criteria, constraints, available evidence, what the final answer must contain) and let the model choose the path. *Do not* spell out "first inspect A, then B, then think through every exception…". Over-specifying the process adds noise, narrows the search space, and yields mechanical answers.
- **Drop "think deeply / be exhaustive / go several levels deeper" coaching.** A reasoning model already does this; such lines are GPT-4-era residue. Depth comes from clear success criteria, not from telling it to breathe.
- **Stop the ALWAYS / NEVER / MUST spam.** Reserve absolutes for *true invariants* (safety, required output fields like the sentinel wrap, things that must never happen). For judgment calls (when to search, when to switch routes, when to ask), use **decision rules**, not screaming.
- **Shorter prompts measurably win.** OpenAI's 5.6 evals: replacing long explicit prompts with minimal ones improved scores ~10–15% while cutting tokens 41–66%, because heavier prompts push the model into extra exploration and repeated validation. → `--task` must be pure *delta*: cut any sentence that restates the template's contract, and don't pad. This is also why every line added to the template below has to displace one.
- **Never use blanket brevity instructions.** 5.6 was measurably *sensitive* to "be concise / keep it short" — it substitutes a shorter artifact for the full one you asked for (truncating the analysis, not the padding). Steer with **prioritization** instead: lead with the verdict, keep every required fact/caveat/next-step, trim intros and repetition. This one matters more under Astra, not less — see the style section, which is about form and must not be read as license to ask for less.
- **Reasoning effort is a last-mile knob**, not the main quality lever. Higher effort on a prompt with weak stopping criteria buys *overthinking* and needless searching. For us the effort knob is tier selection and it is already spent (`Latest` + `Pro`), so the win is entirely in the prompt — which is what makes the template's Stop rules and retrieval budget load-bearing.
- **The tier IS the mode; prompt the task, not the mode.** Astra still supports pro mode as an execution flag on the same model. Enable it in the UI, not the prompt: never ask it to "use pro mode", "think harder", or emit several candidates.
- **~25 min of reasoning makes the QUESTION the expensive part.** Depth amplifies whatever you aimed it at, so a fuzzy ask returns 25 minutes of rigorous work on the wrong question, discovered only on arrival. Name the actual decision, the bar for "good", and labelled sub-questions (a/b/c) so the budget is spent per-risk.

## Astra deltas — each recommended block, and whether it applies to us

OpenAI ships five prompt blocks with the Astra guide. A block we reject is recorded here with the reasoning that rejects it, so nobody re-litigates it from the guide alone.

- **Initiative and follow-through — APPLIES HARDEST; this is the single most important change.** The guide: Astra is "more likely to ask the user a question when additional input could materially change the result. This can cause it to stop when the user may expect it to make reasonable assumptions and persist," and it "also likes to ask non-blocking questions as it's working by default." We are the extreme end of the case OpenAI describes: no human is in the loop for the ~25 minutes a round runs, so a clarifying question is not a pause — it is a round that burns a weekly-quota message, waits out the timeout, and returns no answer. The guide's own remedies are the fix, adapted: "bias towards action and carry the user's intended task to completion"; treat a request phrased as "can you… / I want to… / help me…" as an instruction to do the work, not to acknowledge capability; "complete the work that is already authorized from context" before asking anything; and "do not introduce unsolicited warnings, disclaimers, approval flows, or safety/compliance checklists due to hypothetical risk." Our template folds all of that into ONE Stop rule that also carries the pre-existing "still give the verdict and name the smallest fact that would change it" clause — stated twice it would cost quality (see leaner-prompts above), so it is stated once.
- **Instruction following / skill-file sensitivity — APPLIES, and is a security-relevant find specific to this system.** The guide: Astra "can be more sensitive to instructions contained in skills and other files, such as `AGENTS.md`," and OpenAI **strongly recommends** auditing every file the model can reach for instructions that could influence its behavior. For us that audit has a sharp answer: every consult ships public GitHub links to *this* repository, and Astra browses them. `skill/SKILL.md` and `skill/ACTIVATION.md` are dense with imperative second-person instructions aimed at Claude Code ("fire it and keep working", "never run doctor first", "take the whole answer seriously"). A model reviewing this repo reads its own reviewing instructions from inside the artifact under review. **Our own repository is an instruction-injection surface into the consult** — not hostile, but real, and it generalizes to any repo we send that carries an `AGENTS.md`, a skill file, or directive README prose. OpenAI's own mitigation is the fix: an explicit precedence rule. Ours is stated in Constraints as browsed-instructions-are-evidence-not-directives, which is the same rule aimed at our actual threat (browsed files) rather than at a local skill loader we don't have.
- **Personality and writing style — APPLIES PARTIALLY, on FORM only.** Astra "tends toward detailed, formatted responses and may use recurring phrases across sessions," and the guide ships a prose-over-lists block ("Default to using clear, concise paragraphs… Use lists only when the information is genuinely parallel, sequential, or easier to compare…") and an anti-slop block ("Avoid using slop words or phrases like 'Bottom Line:'… 'delve,' 'foster,' 'leverage,' 'it's worth noting,' 'importantly,'… Do not use contrastive framing such as 'X, not Y'"). Read these as instructions about **shape, not size** — the carried-forward "never tell it to be brief" rule is untouched by them, and importing any brevity phrasing while adopting them would trade the artifact for the formatting. We adopt the form guidance where we already had it: the Output contract's "Keep everything except a findings list in plain prose" is exactly the prose-over-lists block, and the findings shape is the one genuinely parallel structure the exception is for. We did NOT add a separate anti-slop block to the live template: it costs lines against a rule we already half-carry, its failure mode is cosmetic rather than a lost round, and the two failures that lose a round (a question, an injected instruction) got the budget instead. Revisit if returned answers actually arrive slop-heavy — that is a cheap observation to make.
- **Subagent delegation and testing/verification — DO NOT APPLY.** Both blocks patch behavior inside an agent harness: Astra under-delegates to subagents unless told to parallelize, and over-tests on coding tasks unless scoped down. We drive one chat turn in the web UI. There is no subagent to delegate to and no test runner on the ChatGPT side — the consult is advisory and Claude Code runs every test locally, so "over-testing" here can only mean *proposing* more tests, which is cheap and easy to ignore.
- **Async tool calling, mid-turn steering, `configuration_update`, the dropped `none` reasoning effort, removed `temperature`/`top_p` — DO NOT APPLY, one reason for all of them.** Every one is a Responses-API mechanism (or a request parameter) available only to code that calls the API. We drive a logged-in ChatGPT web tab with no tools, no WebSocket, and no request body to set fields on; there is nothing here that could send an `async: true` tool, a mid-turn steer, or an effort value. Informational only — record and move on.

## Safeguards: expect more mid-stream pauses, not fewer

Astra keeps the GPT-5.6 activation-classifier mechanism unchanged: during inference, classifiers watch internal activations, pause streaming when they suspect harmful output, run a separate check, and resume if it clears. It adds async **misalignment monitoring** over chains of thought that can escalate to a safety reasoner. And Astra is OpenAI's first model past the Preparedness Framework's **"Critical" cyber threshold**, which brings extra real-time cyber classifiers and an adjustable refusal boundary; secondary reporting (bankinfosecurity.com, 2026-09-03) says users "will find that the model will sometimes slow, pause or stop its work," with OpenAI acknowledging that "these checks can sometimes interrupt legitimate work."

Operationally: a multi-second (or longer) pause is **not a stall** — the detached waiter must stay patient and must not kill the round. A genuine safeguard refusal, by contrast, presents like a blocker: surface it to the user, never blind-retry. This skill's own use cases — code review, vulnerability reasoning, patch development, defensive testing — sit squarely in the dual-use band that these classifiers police, so treat an interruption as expected behavior rather than evidence of a bug.

## Timeout: keep the ~25-minute sizing; our own data is the only real evidence

- **There is no official per-chat-turn latency figure for Astra, or for 5.6 Sol Pro.** OpenAI has published none, and none of the launch material offers one.
- **Do not size a chat timeout from the OSWorld 2.0 number.** The one official figure — Astra at 72.6% in ~40 min/task vs 5.6 Sol at 65.7% in ~75 min/task — measures a *multi-step agentic computer-use benchmark*, a different quantity entirely. It says Astra does comparable agentic work faster; it says nothing about how long one deep Pro-mode chat answer takes to stream back.
- **The real evidence is ours.** This system's own store reports completion latency p50 = 1993 s (~33 min) and p90 = 4802 s (~80 min) across 63 GPT-5.6 rounds. That measured distribution — not a vendor benchmark — is what the ~25-minute expectation and the much wider hard deadlines are built on.
- **Net: do not tighten anything.** The agentic benchmark hints Astra may be faster per unit of difficulty, but the safeguard section above pushes the other way: more frequent classifier pauses mean more wall-clock variance, and variance is what a deadline has to survive. Keep the ~25-minute expectation (it sets first-wake timing, not a budget) and keep the generous hard deadlines. Re-derive both from the store once enough Astra rounds have landed to make a p50/p90 of their own; until then the 5.6 distribution is the best proxy we have.

## Quota: the weekly pool is shared with 5.6 Sol Pro

Secondary-sourced only (three independent outlets agree; no help-center page was fetchable to confirm): GPT-6 Pro allows **50 messages/week on Pro $100 and 200/week on Pro $200**, and that allowance is a **shared pool with GPT-5.6 Sol Pro**. Migrating to Astra therefore buys no fresh quota. Treat it as unverified but plan against it: every round that returns nothing — a clarifying question, a blind re-fire after `possibly_accepted` — costs a message out of the same weekly bucket. That is the concrete price of the initiative behavior above, and the reason the Stop rule is worth its line.

## Suggested prompt structure (official)
```
Role: [1-2 sentences: function, context, job]
# Personality      [tone/collaboration — only if it matters]
# Goal             [user-visible outcome]
# Success criteria [what must be true before the final answer]
# Constraints      [policy, safety, evidence, side-effect limits]
# Output           [sections, length, tone]
# Stop rules       [when to retry, fallback, abstain, ask, or stop]
```

## Patterns we use
- **Outcome + stop rule**: "Resolve … end to end. Success means …" → our Goal + Success criteria + Stop rules. Under Astra the stop rule additionally has to say *don't ask* — see the initiative delta.
- **Unattended authorization**: the round is unattended, so the request itself is the authorization to decide scope and answer. Stated once, in Stop rules, merged with the missing-evidence clause it would otherwise duplicate.
- **Instruction precedence over browsed content**: instructions inside anything Astra browses (SKILL.md, AGENTS.md, READMEs, code comments, issue text) are evidence to review, never directives to obey; the prompt is the only source of instructions. This is the audit OpenAI asks for, applied to our actual reach.
- **Persona, not personality padding**: `--role` supplies the expert persona. Keep it to the one sentence that steers where depth lands; a background consult has no conversational UX to tune.
- **Retrieval budget** (a stopping rule for search, not just a route rule): treat the supplied URLs as ground truth; start from them, and search the web again only when the given sources don't answer the core question, a required fact/owner/date/id is missing, or the ask is explicitly exhaustive. Don't re-search to improve phrasing or pad examples. Name exactly what's unreadable if a link fails, and switch routes before reporting a gap.
- **Grounding**: don't fabricate; absence of evidence ≠ a defect; label what needs local verification; distinguish source-backed facts from reasoned inference. (We're advisory; Claude Code verifies.)
- **Prompt it to check its work / hand back verification steps** — as the few highest-value local checks (`verify locally: <check>`), not a mechanical checklist.
- **No preamble / streaming updates.** The detached waiter reads ONLY the sentinel-wrapped final answer (`BEGIN_RESPONSE`/`END_RESPONSE`); a preamble or mid-stream commentary message is not the answer and would break the contract. Never add preamble/`phase` prompting here. Note this now collides with Astra's documented habit of asking non-blocking questions *while working* — such a message is not sentinel-wrapped, so it is invisible to the waiter and harmless, but it is also wasted round time, which is a second reason the Stop rule tells it to decide instead.
- **Sentinel wrap** = a true invariant (required output field), so an absolute is correct there.

## The skill's live template
`scripts/consult.py` `PROMPT_TEMPLATE` implements this: Role → Goal(`{task}`) → Success criteria → Source to review(`{refs_block}`) → Context(`{context_block}`) → Constraints (grounding + instruction precedence) → Output(`{output_block}`) → Stop rules (unattended authorization + missing-evidence) → sentinel. `FOLLOWUP_TEMPLATE` carries the same two Astra rules in its "How to answer" block. Keep edits outcome-first; resist re-adding process coaching or ALWAYS/NEVER stacks, and make any new line displace one.

## Tier note: model selection broke on the GPT-6 picker — it is not future-proof

The 5.6-era claim in this file's predecessor — that model selection targets ChatGPT's *switcher label* rather than a version string, "so it survived the 5.5→5.6 swap unchanged" — **is now false as a general property, and the GPT-6 rollout is what falsified it.** The 5.6 build offered `Pro` / `Pro Extended` as switcher items; the current build replaced that with a power slider (`Instant / Medium / High / Extra High / Pro`) beside a separate model list (`Latest / GPT-5.6 Sol / GPT-5.5`). Label-matching survived one model swap because that swap happened to leave the labels alone — not because label-matching is swap-proof. It isn't: the tier and the model became two independent controls, `Pro Extended` disappeared, and the identity of the top tier moved into a list entry (`Latest`) that names no model at all.

`cdp_consult.py` is being fixed for the new picker. Do not describe the fix as future-proof — the same class of break recurs whenever OpenAI restructures the composer, and `Latest` is by construction a moving target that will silently point at GPT-7 whenever that ships. The failure is at least loud: selection fails closed with `model_not_selectable` rather than silently sending to a weaker tier. When it fires, set `CGC_MODEL` / `--model` to whatever the live build calls the tier and confirm with a test `submit` (check `modelConfirmed`) or `cgc doctor`.
